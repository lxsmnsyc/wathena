# Security review, October 2026

This file records the phase 8 step 5 security review (proposal 0002, review decision 51). Each section covers one area of docs/security/threat-model.md. Each finding has its severity, how to reproduce it, and its fix or accepted risk.

## Staff, accounts and database

Findings of the staff and admin, accounts, and database rights areas. Migration 00038 holds the database changes. Each fix has a test that needs PostgreSQL (`WATHENA_TEST_DATABASE_URL`).

### Sanctions had no rank check (high)

- **Finding.** A sanction checked only that the target was not the actor's own account. A game master could ban every admin and owner, and then no one was left who could lift the bans.
- **Reproduce.** As a game master with a recent login, `POST /admin/api/v1/sanctions` with `{"kind": "ban", "accountId": <admin>, "minutes": 60, "reason": "x"}`.
- **Fix.** `server/adminworld` checks the target's rank before a mute, a jail, a kick, a ban and a lift, from the admin API and the GM commands:
  - Only an owner sanctions an owner, or lifts an owner's sanction.
  - A staff account's sanction needs a role of the actor that has every permission of the target's role. This is `Roles.Covers`, the rule of role changes.
  - The admin API answers `forbidden`. A GM command answers with the reason.
- **Accepted risk.** Staff of the same role can still sanction each other, as they can change each other's roles.
- **Tests.** `TestSanctionRank` in `server/adminworld`: a game master's ban of an admin and of an owner, an admin's ban of an owner, a moderator's mute, jail and kick of a game master and an admin, and a moderator's `@mute` of an admin are refused. A game master's lift of an owner's ban of an admin is refused, and an admin's lift works.

### A 10-year ban needed no `moderation.ban_permanent` (low)

- **Finding.** Only a ban with 0 minutes counted as permanent. A game master could ban for 5,256,000 minutes (10 years) with `moderation.ban` alone.
- **Fix.** A ban longer than a year (525,600 minutes, `admin.LongBanMinutes`) needs `moderation.ban_permanent` too, to give and to lift. A year is the longest mute or jail, so one limit holds for every timed sanction that `moderation.ban` gives alone. A longer ban acts as a permanent one, and review decision 35 gave those to admins.
- **Tests.** `TestSanctionCalls` in `server/admin`: a game master's ban of a year and a minute, and of 10 years, are refused, a year works, and the lift of a two-year ban needs `moderation.ban_permanent`.

### The account role could erase the audit log (medium)

- **Finding.** `delete_old_staff_audit` ran as the account role and took the cutoff from the caller, with a floor of 30 days. The account role also inserts reviews, with any reviewer. So it could review every row marked for review and then delete all rows older than 30 days.
- **Reproduce.** As `wathena_account`: insert a review for each unreviewed row, then `SELECT delete_old_staff_audit(now() - interval '721 hours')`.
- **Fix.**
  - The account role can no longer run `delete_old_staff_audit`. The retention job runs it as the game role, which cannot write reviews.
  - A row marked for review goes only once its review is 30 days old, so a new review never frees a row at once.
  - A trigger gives each review the database's time, and refuses a review of a row not marked for review or by the row's own actor.
- **Accepted risk.** A compromised game role can delete rows older than 30 days, before `audit_days`, as it could drop item log partitions before. A compromised account role can still review rows in the name of another account. The floor stays 30 days, the shortest `audit_days`.
- **Tests.** `TestDeleteOldAudit` and `TestAuditReviewRules` in `server/store`, and `TestJob` in `server/retention`.

### The account role could make the deletion job delete accounts at once (medium)

- **Finding.** `wathena_account` could insert any row in `account_deletions`, and `delete_account` trusted the time the game side passed. A request with `delete_after = now()` was deleted at the next hourly run.
- **Reproduce.** As `wathena_account`: `INSERT INTO account_deletions SELECT id, now() - interval '1 day', now() FROM accounts`.
- **Fix.**
  - The account role loses `INSERT` on `account_deletions`. It calls `request_account_deletion(account, wait)`, which sets both times from the database clock and refuses a wait under 14 days.
  - `delete_account` deletes only a request that is due on the database clock, whose wait was at least 14 days. A later time from the caller changes nothing. `DueDeletions` uses the database clock too, so the job does not kick players whose deletion is not due.
- **Tests.** `TestDeletionWaitInDatabase` and `TestAccountPageRights` in `server/store`, and `TestDeletionJob` in `server/adminworld`, which runs the job with the server clock 15 days ahead and checks that nothing is deleted or kicked.

### GM commands worked on a stale staff session (medium)

- **Finding.** The game ticket recorded only the second factor. A stolen staff cookie from weeks ago could get a ticket and use `@item`, which makes items as a restore does, while a restore needs a login from the last 10 minutes.
- **Fix.**
  - The ticket records whether the session proved who its player is within the reauth window when the ticket was made: `game_tickets.recent`, `store.Ticket.Recent` and `staff.Login.Recent`.
  - `staff.NeedsRecentLogin` lists the permissions whose commands need it: `items.create` and the sanctions. `staff.Login.Allows(permission)` gives the answer, and `staff.ReauthText` the message.
  - The zone must check it before it runs a command. The change in `server/zone` is one line in `gmCommand`, after the permission check: `if !p.sess.staff.Allows(c.permission) { z.answer(p, staff.ReauthText); return }`. The dev logins that set `staff.Login{TwoFactor: true}` (`gmcommands.go` and `headless.go`) set `Recent: true` too.
- **Accepted risk.** A game session keeps its ticket's answer until the next login, as it keeps the second factor rule.
- **Tests.** `TestTicketRecordsRecentLogin` in `server/account`.

### Staff read whispers and item history without an audit row (low)

- **Finding.** Report details show the target's chat, whispers too. Character logs, item histories and serial searches show what players own and trade. None wrote an audit row.
- **Fix.** These reads write audit rows: `reports.view`, `characters.logs` (the first page of a search), `items.history` and `players.search_serial`.
- **Tests.** `TestReportCalls`, `TestLogsAndHistory` and `TestPlayerSearch` in `server/admin`.

### Full limiter tables locked out every new name (medium)

- **Finding.** When the name table held 100,000 live entries, every name without an entry was refused for a minute, even with the right password. About 100,000 failed logins with made-up names in an hour filled it.
- **Fix.** A full table pushes out the entry used least recently of a sample of 16, preferring entries without attempts in flight. The per-address buckets do the same. A new name is never refused for lack of room.
- **Accepted risk.** A large flood can push out a name's own failure count early. The per-address buckets still limit the flood.
- **Tests.** `TestFullNameTableDoesNotLockOutNewNames` and `TestFullTablesEvict` in `server/account`.

### The per-name login limit was check-then-act (medium)

- **Finding.** The limiter checked a name's failures before the password hash and counted the failure after it. Guesses sent together all passed the check, so a distributed burst got far more than 5 guesses per wait. The same held for TOTP codes across many pending logins.
- **Fix.** `limiter.reserve` counts an attempt as in flight under the lock of the check. Failures and attempts in flight together reach 5 at most. After that, one attempt at a time goes, after the backoff. The login, the TOTP code, the reauth and the TOTP setup use it.
- **Tests.** `TestConcurrentAttemptsAreReserved` sends 200 attempts at once from different addresses and checks that 5 go through. `TestSweepKeepsAttemptsInFlight` checks that a sweep keeps an attempt in flight.

### A victim could not end a thief's session (low)

- **Finding.** No page ended other sessions, no password change existed, and changing login methods left every other session alive.
- **Fix.**
  - The settings page shows how many other sessions are logged in, with "Log out everywhere else". It needs a login from the last 10 minutes. It ends the other sessions, their logins that wait for a code and their unused tickets, and closes their game connections.
  - A password change, on the settings page with the current password, ends the other sessions the same way.
  - Turning TOTP on or off, new recovery codes, and adding or removing a passkey end the other sessions too.
- **Accepted risk.** The page shows a count, not a list of devices.
- **Tests.** `TestLogOutEverywhere`, `TestPasswordChangeEndsOtherSessions` and `TestLoginMethodChangesEndOtherSessions` in `server/account`.

### Other changes

- `deploy/postgres/roles.sql`, deploy/README.md and server/README.md list the new rights.
- The privacy notice says a row that waits for review is kept until 30 days after its review.
- Decision 0049 and strategy section 7.10 still say the account role runs the audit deletion and that a reviewed row goes at once. This section replaces those lines.

## Zone and gateway

Findings of the protocol and zone area. The tests run without a database.

### The Attack command had no PvP check (high)

- **Finding.** The Attack command took any player in view as a target, so a modified client could hit and kill players anywhere. Only summons were checked.
- **Reproduce.** Send `Attack` with another player's entity ID.
- **Fix.** The Attack command takes a target only when `isEnemy` allows it, as rAthena's `battle_check_target`. `fight()` drops a player's target that is not an enemy, whatever set it. PvP maps are not ported, so players are never enemies. Summons keep the `alchemist_summon_setting` rule.
- **Tests.** `TestSecurityAttackCommandRefusesPlayers` in `server/zone`. `TestOverweightRules` now attacks a monster.

### No rate limits, and one shared command queue (high)

- **Finding.** The gateway limited only chat. Every command went into the zone's one queue of 1024. When it was full, the zone refused the next command of any player, and the gateway disconnected that player. One connection could get every player of a map disconnected.
- **Reproduce.** Send `WalkTo` as fast as the socket allows while other players play on the map.
- **Fix.** Each player may have 64 commands in its zone's queue, so a full share refuses only that player's commands. The gateway limits messages per connection and per kind of command (`server/gateway/limits.go`):
  - All messages: 60 at once, then 30 a second. Chat has its own limit instead.
  - Walks: 20 at once, then 10 a second.
  - Attacks, pick-ups, item use, equipment, stats and skills: 30 at once, then 20 a second.
  - Drops: 10 at once, then 5 a second.
  - NPC clicks, replies and shop commands: 20 at once, then 10 a second.
  - Storage moves: 30 at once, then 20 a second.
  - Party, friend, guild, trade, mail, store, block, report and channel commands: 20 at once, then 5 a second.
  - Store searches: 5 at once, then 1 a second.
  - Pings: 10 at once, then 5 a second.
- **Abuse.** A message over a rate, or a command the queue refused, is dropped and counts as a strike. Strikes fall by one every 100 ms. More than 100 end the connection with `DISCONNECT_REASON_RATE_LIMITED`. A client at twice a kind's rate is only slowed. A flood is disconnected within a second.
- **Why these numbers.** The web client sends a walk at most every 100 ms while the mouse is held. The load test bots think every 100 ms and send at most a walk, an attack, a chat line and a ping each time.
- **Accepted risk.** Connection limits per IP address and a rate limit on `Hello` are not built. They need the client address behind a proxy, which only the account service reads today.
- **Tests.** `TestOneSessionCannotFillTheSharedQueue` in `server/zone`. `TestCommandLimit`, `TestKindOf` and `TestCommandFloodDisconnects` in `server/gateway`.

### Ground item floods disconnected players (high)

- **Finding.** A player could drop a stack one item at a time with no limit. A player who came into view got every item in its first frame. Over 64 KiB, the gateway refused to send the frame and closed the connection, so players near the pile could not stay connected. Each drop also walked every entity of the zone for each cell it tried.
- **Reproduce.** Drop 3000 single items, then let another player walk into view.
- **Fix.**
  - A player may have 50 of its dropped items on the ground at once. Items fade after 60 seconds.
  - A player drops 10 items at once, then one every 200 ms.
  - A map with 2000 ground items takes no more drops from players. Monster loot is not limited.
  - A refused drop gets the new `DROP_ITEM_FAILURE_TOO_MANY`.
  - The zone counts ground items as they are added and removed, so the checks are cheap.
  - A drop, and a kill's loot, walk the entities once for the cells within 2 of the drop, instead of once per cell tried.
  - A tick's events over 64 KiB go out in several frames of the same tick, each under the limit.
- **Why split frames.** A cap on Appear events per tick would bound only appears. A frame also grows from moves in a crowd, combat, chat and other events. Splitting covers all of them in one place. The client already applies several frames of one tick in order, since the zone sends a vanish frame when a player leaves. A single event over the limit cannot happen with the events there are. It would be logged and dropped.
- **Tests.** `TestDropFloodFirstFrameStaysUnderMessageLimit`, `TestDropLimits` and `TestManyGroundItemsSplitFrames` in `server/zone`.

### Ranged attacks went through walls (medium)

- **Finding.** A basic attack only checked the distance, so an archer could shoot over a wall or a cliff, and farm monsters that could not reach it.
- **Reproduce.** Attack a monster 6 cells away with a wall cell between, with a bow of range 9.
- **Fix.** A target 2 or more cells away needs a clear shot through `path.Shoot`, as rAthena's `battle_check_range` with `path_search_long` and `CELL_CHKWALL`. As `unit_attack_timer_sub`:
  - A player that keeps attacking walks toward the target until the shot is clear.
  - A monster walks toward the target with its chase range 2 less.
  - A single attack gives up.
- **Accepted risk.** The distance stays square. rAthena checks a player's attack range as a circle. Changing it could change combat parity, so it is not part of this fix.
- **Tests.** `TestBasicAttackNeedsClearShot` in `server/zone`.

### Hidden players were sent to every viewer (medium)

- **Finding.** A player under Hiding, Cloaking or Chase Walk was sent to everyone in view, with its option bits. A modified client could draw it.
- **Reproduce.** Hide next to another player, and read that player's frames.
- **Fix.** Such a player is sent only to:
  - itself,
  - its party members, its allies in rAthena's `clif_ally_only` rule,
  - viewers with the detector mode, as `status_check_visibility`.
- Viewers who knew the player get a vanish when it hides, and an appear when it shows again. A GM under `@hide` stays hidden from everyone else, as before. rAthena has no GM exception for hidden players, so none was added.
- **Accepted risk.** Hidden monsters are still sent, with their option bits.
- **Tests.** `TestHiddenPlayersAreNotSent` and `TestHiddenPlayersStayVisibleToAllies` in `server/zone`.

### Trade requests filled another player's frame (low)

- **Finding.** Repeated trade requests from one player added one dialog each to the asked player's frame, with no limit.
- **Reproduce.** Send 4000 trade requests to one player within a tick.
- **Fix.** A player with a request open gets no second dialog from the same asker. An asker reaches at most one player a second. A request too soon gets `TRADE_OUTCOME_FAILED`. rAthena has no such limit.
- **Accepted risk.** Friend requests are in `server/social`. The gateway's rate for social commands limits them, but they are not deduplicated.
- **Tests.** `TestRepeatedTradeRequestsDoNotBloatVictimFrame` and `TestTradeRequestsAreThrottled` in `server/zone`.

### The zone did not recover panics (medium)

- **Finding.** Game logic runs on each zone's goroutine, which did not recover panics. A bug in any command handler would stop the process, every zone, and every unsaved change. No trigger was found.
- **Fix.** The zone recovers every panic and logs it with its stack (`server/zone/recover.go`):
  - A command handler's panic ends the sender's session with the new `DISCONNECT_REASON_SERVER_ERROR`. The zone and the other players go on.
  - A panic while the zone builds one player's frame ends that player's connection. The player then leaves with a normal save, since building frames changes no game state.
  - Any other panic stops that zone: in a tick, a script, a commit, a join or a leave. Its players are disconnected with `DISCONNECT_REASON_SERVER_ERROR`, joins get `ErrStopped`, and other zones go on.
- **Why no duplicates.** A handler that panics may have moved items halfway. So:
  - Nothing the handler queued for the next commit is written.
  - The sender, its trade partner, and the players the handler's transfers changed are tainted. A tainted player's session ends with its last saved copy, never with what is in memory. Its logout handlers do not run.
  - When the handler's commit also held storages, guild storages, mail, shop stock, store rows or event units, or the panic came from inside a transfer, the zone cannot tell which objects changed. It stops, and every player of the zone ends with its last saved copy.
  - A tick's panic always stops the zone, since a tick changes items outside transfers, such as loot that falls.
- **Accepted risk.** After such a stop, a storage, guild storage or mailbox that a player in another zone also holds keeps its state in memory. Personal storages load again from the database once no character holds them.
- **Tests.** `TestCommandPanicEndsOnlySender`, `TestTransferPanicStopsZone` and `TestFramePanicEndsOnlyThatPlayer` in `server/zone`.

## Mods and the Lua sandbox

Findings of the mods and Lua sandbox area. Review decision 52 in proposal 0002 approved the changes to the Lua API. The tests run without a database. Each fix's test was seen to fail before the fix.

### Data overlays changed core prices and drops with no permission (high)

- **Finding.** A data overlay checked only the fixed fields, such as an item's ID. A mod with no permissions could raise a core item's sell price, change a monster's drops or exp, change a quest's drops, or make a reserved staff word plain in the chat filter. `rules.override` covers drop rates and `shops.modify` shop costs, so this went around them.
- **Reproduce.** A mod with no permissions and `data/items.yml` `- {name: Jellopy, sell: 2000000000}` loads.
- **Fix.**
  - The new flagged permission `data.core_override` covers the economy fields of records that another mod added, core's too: an item's `buy` and `sell`, a monster's `drops`, `mvp_drops`, `base_exp`, `job_exp` and `mvp_exp`, a quest's `drops`, and a chat filter word's `action` and `match`. A mod's own records need nothing.
  - `wactl mod validate` and `wactl mod install` list the records such a mod changes, as `items Jellopy: sell`.
  - rAthena's `itemdb.cpp` refuses prices that let a player make zeny with Discount and Overcharge: `buy / 124` below `sell / 75`. It sets `sell` to 1 with a warning. wAthena refuses such a record of a mod with an error. Every core price already follows the rule. Two example items set only `sell` and now set `buy` too, as rAthena would make it: twice `sell`.
- **Accepted risk.** A mod's shop can still sell its own item for less than the item's sell price. rAthena only warns about that in `npc.cpp`, and wAthena does not warn yet.
- **Tests.** `TestOverlayCoreEconomyNeedsPermission`, `TestOverlayCoreOverrideAllowed`, `TestOverlayCoreOverrideQuestsAndChat` and `TestItemPricesCannotMakeZeny` in `server/mod`, and `TestInstallListsCoreOverrides` in `tools/modkit`.

### A kept hook next() ran code in another mod's context (high)

- **Finding.** A hook could keep its `next` function and call it after its chain ended. `next` switched the context by the hook's index in whatever chain ran then. A mod's code then ran with another mod's permissions and environment.
- **Reproduce.** Mod M keeps `next` from a `drop_rate` chain and calls it from its `experience` hook, whose chain has mod V's hook at the same index. M's next `drop_rate` hook runs as V and passes V's `game.read` check.
- **Fix.**
  - A `next` stops working once its hook's call returns. Calling a kept `next` raises "the hook that got this next has returned".
  - Each run of a chain has a token. `hook_enter` refuses any token but the running chain's, so no stale or outer `next` can switch the context.
  - The context that a hook replaced comes back from a stack when the hook returns, instead of from the hook's index.
- **Tests.** `TestStoredHookNextKeepsChainContext` and `TestKeptHookNextRaises` in `server/modscript`.

### One mod could use the whole zone's Lua memory (medium)

- **Finding.** Every mod shares the zone's Lua state, and its 16 MB limit was the state's. A mod that kept memory made other mods' calls fail, and those mods were switched off for failing.
- **Reproduce.** Mod A keeps a 1 MB table on each login. After 16 logins, mod B's death handler fails with a memory error, and after 10 failures B is off in that zone.
- **Fix.** Each mod owns the memory its code makes (internal/script, "Owners of memory"):
  - Each Lua block carries its owner in 8 bytes before it. A block that grows belongs to the mod whose code runs. A freed block goes back to its owner, whoever runs then.
  - Each mod has its own limit, 16 MB by default. A call that would go past it stops with a memory error and counts as that mod's failure. Core, the prelude, and memory no mod made share owner 0, with 64 MB.
  - The state has no limit of its own unless one is set: the owners' limits bound it.
  - `lua.wasm` was built again with wasi-sdk 34. Before the change, the build gave the same bytes as the committed file.
- **Accepted risk.** An object one mod keeps that another mod made counts for the mod that made it. A mod that gives a large table to another mod through `require` pays for it.
- **Tests.** `TestHoardingModCannotDisableOtherMods` in `server/modscript`, and `TestOwnerLimits` in `internal/script` with cgo and with `lua.wasm`.

### No CPU budget across calls (medium)

- **Finding.** Each call had a CPU limit, but a mod could make many calls just under it. 40 calls of 15 ms ran in full and none failed, so nothing stopped the mod.
- **Reproduce.** A login handler with a loop of 3,000,000 additions, and 40 logins in a row.
- **Fix.**
  - The binding counts the CPU units it charges, about one per Lua instruction. The runtime gives each run of code to its mod at each switch of context, also between the hooks of one chain.
  - Each mod has a CPU budget per zone tick, 2,000,000 units by default. Once a mod has spent it, its event handlers and hooks are skipped for the rest of the tick, and its timers wait for the next tick. A refusal is not a failure. The zone logs a warning at most once a minute per mod.
  - Setup functions, item, skill and NPC scripts, conversations, schedules and conditions still run, so a player's action is never lost. Their CPU counts.
  - A manifest may ask for another budget with `budget: { memory_mb, cpu_per_tick }`. The owner sets the default with `mods.budget` and the most a manifest may ask for with `mods.max_budget`: 64 MB and 10,000,000 by default. A mod that asks for more does not load. `wactl mod install` shows what a mod asks for.
- **Why these numbers.** The tests of the 21 example mods use at most 15,000 units in one tick and 760 KB of memory per mod. Core's scripts use at most 8 MB in the converter's and the zone's tests. A loop of 3,000,000 additions takes 6,000,000 units and 15 to 27 ms on the development Mac, so the default lets a mod use about 5 to 9 ms of a 50 ms tick.
- **Accepted risk.** Player actions can spend more than the budget, within the per-call limits and the gateway's rate limits. The count hook charges 1,000 units at a time, so CPU goes to the mod that runs when the count is reached.
- **Tests.** `TestSlowButSuccessfulHandlerIsLimited` and `TestBudgetRefusesUntilNextTick` in `server/modscript`, `TestBudgets` and `TestBudgetChecks` in `server/mod`, `TestModBudgetConfig` in `server/cmd/waserver`, and `TestSpent` in `internal/script`.

### player.status was not checked (medium)

- **Finding.** `start_status` and `end_status` checked only that the script could change the game. A mod with no permissions could start any status on a player, such as one that cannot be avoided, for a long time, or end one. The docs said `player.status` gates this.
- **Fix.** Starting and ending a player's status needs `player.status`. Monsters and NPCs need none, and a preview only computes. The verve example asks for it.
- **Tests.** `TestStartStatusNeedsPermission` in `server/modscript`.

### Mods could pass for players and read private chat (medium)

- **Finding.** `player:whisper` took any `from` up to 24 characters, so a mod could whisper as a player or as staff, such as to ask for a password. Announcements did not say where they came from. The `chat` event gave every mod the text of whispers between players.
- **Fix.**
  - `ChatMessage` has the new field `from_mod`: the ID of the mod whose script sent a whisper or an announcement. Core's lines have none.
  - The client shows a mod's whisper as a server line, `[Mod example.bank] Banker: text`, which opens no whisper tab to answer, and a mod's announcement with the same mark.
  - The `chat` event delivers whispers, party lines and guild lines only to a mod with `rules.override`. The `chat` hook already needed it and saw every line.
- **Tests.** `TestWhisperCannotImpersonatePlayer`, `TestChatEventHidesWhispers`, `TestChatEventPrivateLinesNeedPermission` and `TestCoreWhisperIsNotMarked` in `server/modscript`, `TestAnnouncements` in `server/zone`, and the client's `online.test.ts`.

### Mods reached other mods' storages (medium)

- **Finding.** A storage name with another mod's prefix found that mod's record, so any mod could open, count and take from other mods' extra storages.
- **Fix.** A mod reaches only its own extra storages and core's (core has none). The server's own calls still reach every record. The account's storage and the cart keep the permissions the API reference names: none to open and take, `game.read` to count, and `player.give_items` to give.
- **Accepted risk.** Taking items from a player's own storage or cart needs no permission, as the API reference says.
- **Tests.** `TestStorageRecordOfOtherModIsHidden` and `TestStorageRecordOwnAndServer` in `server/zone`.

### Variables and statuses grew without limit (medium)

- **Finding.** Each `variables.*` declaration added an entry, even for the same variable, and nothing freed it. `statuses.define` and server variables had no count per mod, and one mod could take a player's whole share of 4,096 variables.
- **Fix.**
  - Declaring the same variable again gives the same handle. A mod declares at most 256 variables.
  - A mod's values take at most 1 MiB as JSON on one player, and its server variables at most 256 values and 1 MiB.
  - A mod defines at most 256 statuses.
  - Each limit raises an error that names it.
- **Tests.** `TestRedeclaringVariableDoesNotGrow` and `TestModVariableLimit` in `server/modscript`, `TestModVariableBytesPerPlayer` in `server/zone`, `TestModLimits` in `server/variables`, and `TestDefineLimit` in `server/statuschange`.

### load and memory addresses reached mods (low)

- **Finding.** Strategy section 7.7 says mods have no `load`, but their environment had one. `tostring` and `string.format` showed the heap addresses of tables and functions, which help an attack on C Lua.
- **Fix.** Mods have no `load`. `tostring` shows a table, a function or a coroutine as its kind and a number, such as `table: #12`. `string.format` shows `%s` the same way and refuses `%p`, also as a string method.
- **Accepted risk.** The order of `pairs` over a table with table keys still depends on addresses.
- **Tests.** `TestNoHeapAddresses` and `TestEnvironmentIsolation` in `server/modscript`.

### Mod files were read before their size was checked (low)

- **Finding.** The server read each `.lua` file of a mod and checked the total after. A `.zip` entry can state any size, and the reader sized its buffer from it. Manifests and data files had no limit.
- **Fix.** Each file's size is checked before it is read, and the read stops at the limit: 64 KB for `mod.yaml`, 32 MB for a data file, 8 MB for all scripts, and 4 MB for the locale. `wactl` checks the same.
- **Tests.** `TestZipModLimits` and `TestReadLimited` in `server/mod`.

### Unsigned mod packages install (low)

- **Finding.** `wactl mod install` installs a `.zip` file without a checksum or a signature with only a note. A `.sha256` file next to the `.zip` comes from the same place, so it proves only that the download is whole.
- **Accepted risk.** mods/README.md now says so, and says to compare the checksum with one the author publishes elsewhere or to use `--public-key`. Required signatures are phase 9 work.

### Other changes

- mods/README.md, server/README.md, strategy sections 3.8 and 7.7, internal/script/README.md and the threat model describe the changes. The API reference in docs/generated was made again.
- The threat model's finding 1, per-mod memory limits, is resolved without a Lua state per mod.
